Fase 01. Gestión comercial y atención inicial

1.1 Contexto del cliente

El cliente es un grupo de pequeños y medianos productores agrícolas dedicados al cultivo de café y plátano en zonas de altura. Necesitan una plataforma que permita registrar, consultar y dar trazabilidad a las labores realizadas en cada lote agrícola, asegurando transparencia entre trabajadores de campo y la administración.

1.2 Necesidad detectada

  • Ausencia de un registro centralizado de labores (fertilización, fumigación, poda, riego, cosecha, siembra).
  • Dificultad para conocer el estado actual de un lote al escanear su código QR físico.
  • Falta de trazabilidad entre la aplicación de insumos y la cosecha final.
  • Necesidad de diferenciar niveles de acceso: trabajador de campo (público vía QR) y administrador (panel privado).

1.3 Alcance del proyecto

Desarrollo de una aplicación web Full Stack tipo SPA que permita:

  • Consulta pública de lotes mediante escaneo de código QR (sin autenticación).
  • Panel de administración autenticado con dashboard, gestión de lotes, labores, cultivos, insumos, fincas y usuarios.
  • Sincronización de información en todos los apartados mediante un estado global centralizado.

Fase 03. Scrum, arquitectura y diseño

3.1 Metodología Scrum aplicada

El proyecto se organizó en entregas incrementales por módulo funcional. Cada sprint entregó un dominio completo con sus 5 capas backend y su correspondiente vista frontend, integrando pruebas de funcionamiento antes de pasar al siguiente módulo.

3.2 Reglas de arquitectura (obligatorias)

  • No escribir lógica de negocio en los Controladores (solo rutas HTTP y respuestas).
  • No escribir consultas SQL/SQLAlchemy en los Servicios (delegar al Repositorio).
  • No acceder a la base de datos directamente desde los Controladores (usar Servicios).
  • Usar Type Hinting y Docstrings en todo el código Python.
  • Usar manejo de excepciones personalizado (AppException en shared/utils/).

Fase 05. Desarrollo incremental

5.1 Módulo de usuarios (autenticación)

Implementación completa de login/logout, protección de rutas por rol (SUPERADMIN, ADMIN, MAYORDOMO), y gestión de usuarios con asignación de finca. El controlador expone endpoints POST /api/auth/login, POST /api/auth/logout y GET /api/auth/me.

5.2 Módulo de lotes (consulta pública QR)

Endpoint público GET /api/lotes/qr/<codigo_qr> que devuelve datos del lote (nombre, estado, cultivo, hectáreas) solo si el lote está ACTIVO. No requiere autenticación.

5.3 Módulo de cultivos (catálogo)

API REST completa con operaciones CRUD sobre cultivos: listar, obtener por id, crear, actualizar y eliminar. Incluye validaciones de nombre único y campos obligatorios.

5.4 Módulo de labores

API REST completa para registro, consulta, actualización y eliminación de labores agrícolas (siembra, fertilización, fumigación, poda, riego, cosecha) asociadas a fincas y lotes.

5.4 Frontend SPA

Aplicación de una sola página con enrutamiento del lado del cliente, gestión de estado centralizada (store.js con patrón observador), componentes reutilizables (Modal, StatusBadge, KpiCard, FincaSelector) y vistas para dashboard, lotes, labores, cultivos, insumos, fincas, usuarios y calendario. Todos los apartados están sincronizados mediante el store global.

Comunicación entre componentes

  • Frontend → Backend: peticiones fetch asíncronas con JSON a través de apiClient.js.
  • Backend → Base de datos: consultas SQLAlchemy a través de repositorios.
  • Frontend interno: store global pub/sub que mantiene sincronizados dashboard, lotes, labores, cultivos, insumos, fincas y usuarios. Cualquier creación/edición/eliminación se refleja inmediatamente en todas las vistas.
  • Errores: manejo centralizado con AppException que respuestas JSON con código HTTP y mensaje amigable.

Diseño de seguridad

  • Autenticación: Flask-Login gestiona sesiones de usuario. Las contraseñas se almacenan hasheadas con Flask-Bcrypt (never plain text).
  • Autorización por roles: decorador admin_required protege rutas para SUPERADMIN y ADMIN. Los MAYORDOMO solo ven su finca asignada.
  • Endpoints públicos: la consulta de lotes por QR no requiere autenticación y solo expone datos no sensibles (nombre, estado, cultivo, hectáreas).
  • Validación de entrada: todos los payloads se validan con Marshmallow antes de llegar al servicio.
  • Manejo de excepciones: AppException devuelve códigos HTTP apropiados (400, 401, 403, 404, 409, 500) sin exponer detalles internos del servidor.
  • Variables de entorno: SECRET_KEY y credenciales de BD en archivo .env (ignorado por Git, no se suben secretos).

Decisiones arquitectónicas (ADR)

ADR-01: Monolito modular por capas

Decisión: Organizar el backend como monolito modular con separación estricta de controladores, servicios, repositorios, entidades y DTOs por dominio.

Alternativas consideradas: microservicios, arquitectura en capas tradicional sin separación por dominio.

Justificación: Proyecto de alcance académico con un equipo reducido; el monolito modular facilita desarrollo, pruebas y despliegue en un solo servidor, mientras que la separación por capas garantiza mantenibilidad y testabilidad.

ADR-02: SPA vanilla JavaScript sin frameworks de interfaz

Decisión: Construir el frontend con HTML/CSS/JS puro y Bootstrap 5, sin React, Angular ni Vue.

Alternativas consideradas: React, Vue.js, Angular.

Justificación: Requisito explícito de la asignatura. Además, reduce dependencias, tiempo de compilación y complejidad para un proyecto de este tamaño.

ADR-03: Estado global con store pub/sub

Decisión: Implementar un store centralizado (patrón observador) en JavaScript para sincronizar datos entre todas las vistas del SPA.

Alternativas consideradas: estado local por vista, localStorage, Context API (React).

Justificación: Garantiza que la información se mantenga sincronizada en todos los apartados (dashboard, lotes, labores, cultivos, insumos, fincas, usuarios) sin recargas de página.

ADR-04: Flask-Migrate para gestión de esquema

Decisión: Agregar Flask-Migrate/Alembic para control de versiones de la base de datos.

Alternativas consideradas: scripts SQL manuales únicamente.

Justificación: Requisito técnico del proyecto (gestión de migraciones de base de datos) y buena práctica para evolucionar el esquema de forma controlada.

Consideraciones de calidad

Rendimiento

  • Endpoints públicos (QR) optimizados para consultas simples sin autenticación.
  • Uso de índices en claves foráneas y campos de búsqueda (código QR, finca, lote, fecha).
  • Frontend sin build step: carga inmediata de assets estáticos.

Escalabilidad

  • Arquitectura modular permite agregar nuevos dominios sin afectar los existentes.
  • Separación de capas facilita reemplazar la base de datos o agregar servicios externos.
  • Posibilidad de escalar horizontalmente colocando Flask detrás de un WSGI y proxy inverso (Nginx/Apache).

Disponibilidad

  • Servidor Flask ligero apto para desarrollo y despliegue en pequeños servidores.
  • Manejo centralizado de errores evita fallos silenciosos.
  • Base de datos MySQL con motor InnoDB soporta transacciones y concurrencia.

Seguridad

  • Contraseñas hasheadas con Bcrypt.
  • Control de acceso por roles y finca asignada.
  • Validación de entrada en cliente y servidor.
  • No se exponen secretos ni credenciales en el código.

Costos y riesgos

  • Costos bajos: tecnologías de código abierto (Flask, MySQL, Bootstrap, JavaScript vanilla).
  • Riesgo mitigado: dependencia de CDN para Bootstrap (mitigada con fallback local si fuera necesario en producción).
  • Riesgo mitigado: ausencia de autenticación en endpoint QR (aceptable por diseño, solo datos no sensibles).
